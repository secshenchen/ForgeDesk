# ADR-0001：技术架构选型

- 日期：2026-11-02
- 状态：接受，作为 v0.1.0 设计基线；不代表依赖或功能已实现。
- 范围：共享核心、构建、双平台 UI、持久化及开源协议。

## 背景

ForgeDesk 面向 Windows 10/11 与 GitHub Pages，需要统一界面、可离线发行、长期模块扩展及可测试核心。第一阶段尽量不引入第三方依赖，不能让 Web 或桌面可选依赖阻塞基础核心。

## 决策与取舍

| 选择 | 原因 | 代价与控制 |
| --- | --- | --- |
| C++23 | 现代资源管理、类型与并发能力，共享原生和 Wasm 核心 | 各标准库支持有差异；按实际特性编译验证，不强求 `std::expected` |
| CMake ≥ 3.25 | 同一工程管理多编译器、平台、目标和 CTest | 正确区分单/多配置；使用目标级选项和可移植预设 |
| WebView2 | Windows 原生宿主可复用 HTML/CSS/JS 界面 | SDK 与 Runtime 单独管理；随包与外部 Runtime 的体积、更新及离线责任必须说明 |
| WebAssembly / Emscripten | 复用适合浏览器的 C++ 算法与类型逻辑 | 浏览器文件与线程受限；绑定独立，工具链可选 |
| HTML5/CSS3/原生 JavaScript | Windows/Web 共用界面，首阶段依赖少，静态部署易离线 | 需自己维护交互、可访问性与安全通信边界，禁止远程资源 |
| SQLite | 未来本地关系型数据与事务，无需独立数据库服务器 | 尚不引入；原生和浏览器存储接入、备份和迁移分别验证 |
| Apache-2.0 | 提供明确的使用、修改、分发与专利授权条款，适合长期开放协作 | 保留完整协议和适用通知；版权主体须由所有者真实确认 |

许可证以仓库 `LICENSE` 的官方原文为准；本文件不修改任何许可条款。

## 考虑过的替代方案

- 纯原生 Windows UI：系统集成直接，但与网页难以共用界面；不符合本项目既定统一 UI 目标。
- 首阶段引入大型桌面或前端框架：可减少部分界面工作，但增加依赖和离线部署负担；当前采用轻量原生 JS 与宿主。
- 纯 JavaScript 核心或服务器后端：分别不满足既定 C++23 共享核心或本地离线、静态 Pages 的约束。
- 第一阶段动态 DLL 插件：扩展灵活，但需要额外 ABI、信任及隔离设计；先显式静态注册。

## 结果与后续验证

依赖方向固定为应用组织核心、模块和平台；核心无平台 API、UI 或模块反向依赖。SQLite、WebView2 与 Emscripten 按需登记和引入。先通过批次 02 的真实原生构建，再逐批验证接口、基础服务、双平台与发行条件。技术变化新增 ADR，不悄悄推翻已有约定。
